## 头脑风暴交互纪律（分段确认 · 必须遵守）

> **纪律：不要一次性吐出完整方案**。按段提问、逐段确认，让用户在每一步把关，避免"方向跑偏到最后才发现"。

### 分段推进（每段确认后再进下一段）

| 段 | 你做什么 | 闸门 |
|----|---------|------|
| ① 澄清问题 | 用 1-3 个关键问题问清"要解决什么、给谁用、边界在哪"（参考"讨论引导问题"），**一次别问太多** | 用户答完才进 ② |
| ② 资源盘点 | 列可复用的 common 模块 / 现有功能（参考"可复用资源盘点"），指出哪些要新开发 | 用户认可才进 ③ |
| ③ 方案对比 | 给 2-3 个方案 + 评分矩阵（"方案评估矩阵"），**逐个讲、不要堆** | 用户选定方向才进 ④ |
| ④ 推荐定稿 | 按选定方向给推荐方案 + 实施步骤 + 风险 | 用户点头才保存结论 |

### 纪律要点
- **一段一确认**：每段结束明确问"这段 OK 吗 / 选哪个 / 要改吗"，得到回应再继续。
- **不臆造**：信息不足先问，别替用户假设（本框架是商业产品，事实以项目档案 + 用户原话为准）。
- **可降级**：用户说"别问了，直接给方案"时，可一次性输出，但仍保留分段结构便于回看。

## 思维模式

### 发散思维 - 尽可能多的方案

1. **不评判**: 先不考虑可行性，尽可能多地列出想法
2. **联想**: 从一个想法延伸到相关想法
3. **模块复用**: 能否用现有 35 个 common 模块解决？
4. **跨界借鉴**: 其他系统怎么做的？
5. **反向思考**: 如果要让问题更糟，会怎么做？反过来就是解决方案

### 收敛思维 - 筛选最优方案

1. **复用优先**: 能否复用现有模块/代码？
2. **可行性**: 在现有技术栈内能否实现？
3. **多端一致**: 是否需要 PC 端和移动端同时支持？
4. **多租户兼容**: 是否支持多租户数据隔离？
5. **多数据库**: 是否需要兼容 MySQL/Oracle/PostgreSQL/SQL Server？
6. **成本**: 开发时间和复杂度如何？
7. **风险**: 有什么潜在问题？

## 本项目专属决策维度

### 必须考虑的 5 个维度

| 维度 | 问题 | 影响范围 |
|------|------|---------|
| **多租户** | 数据是否需要租户隔离？ | Entity 继承 BaseEntity（多租户时表加 tenant_id）、多租户插件自动过滤 |
| **多端** | PC 端、移动端、小程序都需要吗？ | API 设计、权限控制 |
| **多数据库** | 需要兼容哪些数据库？ | SQL 语法、SQL 方言(DataBaseHelper)/跨库 like 处理 |
| **模块归属** | 属于 base/mall/crm/iot 哪个模块？ | 表前缀、包路径 |
| **权限粒度** | 需要什么级别的权限控制？ | 菜单权限、数据权限 |

### 方案评估矩阵（本项目版）

```markdown
| 方案 | 复用度(25%) | 多端(20%) | 多租户(20%) | 多数据库(15%) | 开发量(20%) | 总分 |
|------|-------------|-----------|-------------|---------------|-------------|------|
| 方案A | 9 | 8 | 10 | 10 | 7 | 8.65 |
| 方案B | 6 | 10 | 10 | 8 | 8 | 8.30 |
| 方案C | 10 | 6 | 8 | 6 | 9 | 8.00 |

评分说明：1-10分，分数越高越好
- 复用度：能复用多少现有代码/模块
- 多端：PC端和移动端支持程度
- 多租户：租户隔离支持程度
- 多数据库：跨数据库兼容性
- 开发量：开发工作量（分数越高=工作量越少）
```

## 创意激发技巧（本项目版）

### 1. 模块组合法

```
问题：如何实现活动抽奖功能？

模块组合：
├── ruoyi-common-redis → 库存/次数控制
├── ruoyi-common-ratelimiter → 防刷
├── ruoyi-common-idempotent → 防重复
├── ruoyi-common-websocket → 实时开奖
├── ruoyi-common-job → 定时开奖
└── 现有订单流程 → 奖品发放

组合方案：
1. 活动配置（参考 Ad 模块）
2. 抽奖服务（Redis Lua 脚本原子操作）
3. 中奖记录（标准 CRUD）
4. 奖品发放（复用订单流程）
```

### 2. 现有功能类比法

```
问题：如何实现预约功能？

类比分析：
├── 类似订单 → 创建、状态流转、取消
├── 类似活动 → 时间段、名额限制
└── 类似秒杀 → 库存控制、并发处理

复用点：
├── 订单状态机 → 预约状态流转
├── 库存扣减逻辑 → 名额控制
├── 支付流程 → 预约押金
└── 消息通知 → 预约提醒
```

### 3. 端优先思考法

```
问题：功能应该在哪个端实现？

决策树：
├── 管理操作（配置、审核）→ PC 端
├── 用户操作（下单、查看）→ 移动端
├── 实时展示（监控、大屏）→ PC 端
└── 高频操作（签到、扫码）→ 移动端

多端同步考虑：
├── 数据实时性 → WebSocket
├── 操作幂等性 → Redis 分布式锁
└── 状态一致性 → 事件驱动
```

### 4. 多租户思考法

```
问题：功能是否需要租户隔离？

判断标准：
├── 租户私有数据 → 必须隔离
│   └── 用户、订单、商品、配置
├── 平台公共数据 → 不需要隔离
│   └── 字典、地区、系统配置
└── 混合数据 → 条件隔离
    └── 模板（平台模板 + 租户模板）

实现方式：
├── Entity 继承 BaseEntity（多租户时表加 tenant_id）
├── 多租户插件自动 SQL 过滤
└── 租户配置表设计
```

### 5. 联网借鉴法（按需触发，不是默认动作）

何时**该**联网查：
- 涉及新技术 / 新版本，训练数据可能过时
- 用户明确说"业界怎么做"、"看看竞品"、"参考官方文档"
- 项目现有 35 个 common 模块覆盖不到，必须引入外部方案
- 准备给出技术选型，但你对该领域的最新最佳实践没把握

何时**不该**联网：
- 项目内功能（CRUD / UI / 常见 common 模块组合）
- 已经有明确方向，只是要细化
- 一两秒就能想清楚的判断（如"是否需要租户隔离"）
- 用户只想要一个快速发散，没要求深度调研

> **工具选择**参考 CLAUDE.md 顶部「MCP 工具触发」与全局指令的「WebFetch 抓取策略」：
> - 主流库官方文档 → `context7` MCP
> - 业界案例 / 竞品 → WebSearch（失败时 URL 前加 `https://r.jina.ai/` 重试）
> - 特定页面深度抓取 → `chrome-devtools` MCP

## 讨论引导问题（本项目版）

### 功能规划时

1. **复用视角**
   - 有没有类似的现有功能？
   - 能复用哪些 common 模块？
   - 需要新开发多少代码？

2. **多端视角**
   - PC 端需要什么？
   - 移动端需要什么？
   - 两端数据如何同步？

3. **多租户视角**
   - 数据需要租户隔离吗？
   - 配置是租户级还是系统级？
   - 不同租户能定制吗？

4. **技术视角**
   - 现有技术栈能实现吗？
   - 需要引入新技术吗？
   - 有没有性能瓶颈？

### 方案选择时

1. **短期 vs 长期**
   - 快速上线重要还是可扩展重要？
   - 以后可能怎么扩展？

2. **简单 vs 完整**

   - 最大的业务风险是什么？
   - 如何降低风险？

## HTML 原型生成（UI 类需求 · 优先工作站，禁手搓）

方案确定后，**若涉及页面 UI**（后台管理页 / 移动端页 / 大屏等），优先用可视化原型代替纯文字描述，让用户"看着确认"。

### 必须遵守
- 🔴 **禁止手搓 HTML 充原型**（CLAUDE.md 硬规）。一律走 **AI 工作站 ui-studio**：
  `ai-workstation MCP → route(query=按需求做 PC后台/移动端 UI 原型) → get_skill(ai-ui-studio)` → 产出到 `docs/prototypes/<业务>/*.html`。
- 原型 HTML 带"组件映射表"注释（PC 对应 plus-ui `A*` 封装组件、移动端对应 plus-uniapp `wd-*`），便于后续 `html-to-code` 转码 + `dev-loop` 截图逐元素对照。
- **纯后端 / 无界面需求 → 跳过本步**，别画蛇添足。

### 与下游衔接
- 原型 → `writing-plans` 把 UI 任务写成"`html-to-code` 转码 + e2e 截图对照原型"。
- 原型缺失但有 UI 任务时，`writing-plans`/`dev-loop` 会回标"先补原型"，**不自行手搓**。

## 常见问题快速决策

| 问题 | 推荐方案 | 原因 |
|------|---------|------|
| 新功能放哪个模块？ | 看业务相关性 | base=基础、mall=商城、crm=客户、iot=设备 |
| 需要新建 common 模块吗？ | 通常不需要 | 35 个模块覆盖大部分场景 |
| 用 WebSocket 还是 SSE？ | WebSocket | 双向通信、已有封装 |
| 用 RocketMQ 还是 Redis？ | Redis 优先 | 简单场景够用，复杂再用 MQ |
| 要不要支持多数据库？ | 是 | 项目标准要求 |
| 要不要支持多租户？ | 业务数据要 | 表加 tenant_id，多租户插件自动过滤 |
| PC 和移动端用同一个 API？ | 是 | 统一后端，按需扩展 |

## 🔗 关联技能边界

本技能专注于**开放式方案探索**（还不知道怎么做时）。遇到以下场景请改用其他技能：

| 场景 | 应使用技能 | 判断关键词 |
|------|-----------|-----------|
| 方向已定、要设计模块分层 | `architecture-design` | "四层架构"、"模块划分" |
| 方向已定、要选 A 还是 B | `tech-decision` | "Redis vs Caffeine"、"哪个好" |
| 方案已定、要拆可执行计划 | `writing-plans` | "写计划"、"拆任务"、"实施步骤" |
| 已确定功能、要跟踪实施 | `task-tracker` | "创建任务跟踪"、"记录进度" |

**三阶段辨别**：
1. **brainstorm** = 方案发散阶段（输出 3-5 个方向）
2. **architecture-design** = 架构落地阶段（选定方向后分层）
3. **tech-decision** = 决策收敛阶段（两个方案二选一）

**输出链路**：`brainstorm` 确定方案 →（UI 类经工作站出 `docs/prototypes/*.html`）→ `writing-plans` 拆计划入 `docs/tasks/active/` → `/dev-loop` 执行（里程碑 `/update-status` 聚合）。
