# 决策记录（Architecture Decision Records, ADR）

> 记录「为什么这么做」的架构取舍，防止后续 AI 协作者或维护者误解设计意图、重复造轮子、或把「有意为之」的取舍当成缺陷返工。
>
> 只记**不可从代码一眼看出的、有取舍的决策**；代码本身能说明的事实不要记 ADR。

## 何时写 ADR

满足以下**任一**条件，就值得记一条：

1. 做了一个「有多种合理方案」的取舍，后续读者可能倾向选另一种。
2. 一段代码看起来「冗余/过度设计/反常」，但它是**有意为之**的（如刻意保留的防御分支、刻意的双实现）。
3. 一个「safety/一致性」机制的存在理由无法从代码体现（如「为什么 handler 层先校验租户，store 层不限定」）。
4. 一个被**反复问起**或**反复想改掉**的设计点。

## 何时不写

- 纯 bug 修复（直接改即可）。
- 代码一眼能看懂的常规实现。
- 「事后找补」的漫长过程叙述（ADRs 记录的是**结果与理由**，不是推导全流程）。

## 文件格式

- 位置：`docs/decisions/`。
- 命名：`NNNN-<slug>.md`，`NNNN` 为 4 位递增序号，slug 用小写连字符英文短语。
- 模板见 [`0000-template.md`](0000-template.md)。
- 每条 ADR 是不可变的历史快照：**已接受的决策不改写**，若要改变决策，写一条**新 ADR** 并用「取代」字段指向被取代的那条。

## 索引与状态

- 每条 ADR 头部标注状态：`提议 / 已接受 / 已取代 / 已废弃`。
- `docs/decisions/` 下的 README（本文件）维护一个**索引表**（序号、标题、状态、一句话结论），新增 ADR 时同步登记到这里。
