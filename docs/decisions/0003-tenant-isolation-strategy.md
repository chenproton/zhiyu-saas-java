# 0003: 租户隔离采用「handler 层校验 + SQL 层可选限定」

- 状态：已接受
- 日期：2026-08-14

## 背景

多租户隔离有两条防线可选：① handler 层先查归属再校验（`GetByID` + `verifyTenantOwnership`）；② store 层 SQL 直接加 `AND tenant_id = $n`。前者灵活但依赖调用方自觉，后者严格但改动面大、且部分查询（如内部回查）本就不需要租户参数。

## 决策

我决定采用「**handler 层校验为主，SQL 层租户限定为可选纵深防御**」：

- 关键写操作（考试题目增删改分、密码/状态写）在 SQL 层补租户条件，作为「漏校验即 IDOR」的纵深防御。
- 普通读/写依赖 handler 层 `GetByID` + `verifyTenantOwnership` 校验，store 层不加租户限定。
- dict 类 store / organizations 等，靠 crud 框架的 `CheckOwnership` + `GetOwnership` 统一兜底。

## 备选方案

1. **所有 SQL 一律带租户条件**：最严格，但 store 方法签名全面膨胀、大量「内部回查」需穿透租户参数，且需改造泛型基类和数十调用点，收益与成本不匹配。部分否决（仅关键写操作采纳）。
2. **只靠 handler 校验，SQL 永不限定**：简单，但任一新调用点漏校验即成越权。否决（需配合关键写操作的 SQL 纵深防御）。

## 后果

### 正面
- 关键写操作有双重防线，普通路径不被租户参数拖累。
- 越权校验位置明确（handler 层），新协作者/AI 易对齐。

### 负面 / 代价
- 「哪些操作该在 SQL 层补租户」需要经验判断，边界不完全机械化。
- store 层「无租户限定」的方法依赖注释/审查保证调用方校验，存在未来新调用点遗漏的风险（需 ADR 标注契约 + 审查兜底）。
