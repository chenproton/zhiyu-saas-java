# 性能与可维护性最佳实践

> 本文档汇总当前审计中发现的可优化项，并提出设计层面的最佳实践方案。范围限定在性能与可维护性，不涉及安全改造。
> 按“简单优先、小步快跑”原则，方案分为“立即收益高且改动小”和“长期收益但改动较大”两类。

## 一、Portal 工作台聚合查询优化

### 现状
- `PortalHandler.WorkspaceDashboard` 单次请求执行 10+ 次 DB 查询，无缓存。
- 教师/学生工作台是高频入口，开学、考试前容易出现并发峰值。

### 最佳实践
1. **查询合并**：将工作台所需的公告、待办、日程、统计、课程列表等数据合并为 1-3 条聚合 SQL，使用 CTE 或一次性 JOIN 减少 RTT。
2. **短周期缓存**：对非实时敏感数据（如课程数、学生数、待考考试数）设置 30-60 秒缓存，缓存键按 `tenant_id + role + user_id` 组合。
3. **按需加载**：工作台首屏只加载关键卡片数据，详情列表（如完整考试列表、场景任务）通过独立接口懒加载或分页。
4. **后台预计算**：学分、出勤率、场景完成状态等可接受分钟级延迟的指标，由定时任务或事件触发预计算并写入缓存或冗余字段。

### 预期收益
- 降低工作台 P99 响应时间。
- 减少数据库并发压力。

## 二、统一导入导出格式

### 现状
- 通用 `ImportExportHandler` 提供 CSV 导入导出（5 种实体）。
- 各业务平台又单独实现 Excel 导入导出（岗位、场景、课程、题库、试卷、基础数据）。
- 两套模板、两种解析逻辑，维护成本高，用户也容易混淆。

### 最佳实践
1. **统一为 Excel**：所有批量导入导出统一使用 Excel 格式，保留表头中文提示、字典预填充、多 sheet 能力。
2. **逐步下线 CSV**：将 `ImportExportHandler` 的 CSV 能力标记为 deprecated，新增 Excel 替代接口，前端迁移完成后删除 CSV 路径。
3. **抽象导入管线**：抽取公共的“上传 → 解析 → 校验 → 预览 → 执行”流程，各业务只需提供 sheet 定义和行转换函数，减少重复代码。

### 预期收益
- 降低模板维护成本。
- 提升用户体验（Excel 可直接查看格式）。

## 三、内容状态机收敛

### 现状
- 岗位/场景/课程/题库/试卷使用通用 6 状态模型。
- 商城资源使用独立 6 状态模型（`draft/reviewing/pending_publish/rejected/published/offlined`），与通用状态机不兼容。

### 最佳实践
1. **状态语义映射**：
   - `reviewing` / `pending_publish` 可映射为通用 `pending`。
   - `offlined` 可映射为通用 `archived`。
2. **收敛到通用状态机**：资源 `ResourceHandler` 复用 `contentActions` 的状态流转、save-draft、归档、恢复逻辑。
3. **保留业务语义别名**：在 UI 层保留“审核中/待发布/已下架”等中文文案，底层统一使用通用状态。

### 预期收益
- 减少一套状态维护逻辑。
- 统一审批、归档、恢复入口。

## 四、大事务拆分与异步化

### 现状
- 岗位 `SaveFull` 单事务写入 5+ 张表。
- 订单 `Pay` 单事务完成 5 个写操作。
- 并发高时大事务会拉长锁持有时间，影响吞吐。

### 最佳实践
1. **核心一致性操作保留事务**：资金变动、库存扣减等必须强一致的关键步骤保留在同一事务内。
2. **非关键步骤异步化**：
   - 岗位保存后的视图计数初始化、索引更新可异步。
   - 订单支付后的销量统计、通知记录可异步。
3. **补偿机制**：对异步步骤提供失败重试和补偿任务，保证最终一致性。
4. **批量导入事务边界**：对 Excel 批量导入，按 sheet 或按批次包裹事务，失败时回滚当前批次，而不是全部行逐条提交。

### 预期收益
- 缩短关键事务持有锁的时间。
- 提升并发写入能力。

## 五、业务规则配置化

### 现状
- Portal 工作台学分计算为 `总课时 / 16`，硬编码在代码中。
- 类似硬编码规则未来调整时需要发版。

### 最佳实践
1. **平台配置表扩展**：在 `platform_configs` 或新增 `tenant_settings` 表中存储学分换算比例、学期开始日期、默认考试及格线等业务规则。
2. **租户级覆盖**：允许不同租户覆盖默认配置，满足学校个性化需求。
3. **配置热加载**：读取后缓存，变更时通过缓存失效或消息通知刷新。

### 预期收益
- 业务规则调整无需发版。
- 支持租户差异化配置。

## 六、审计日志与大数据表治理

### 现状
- `operation_logs`、`login_logs`、`view_logs` 等表持续写入，随时间线性增长。
- 商城资源删除前检查 `orders`、`authorizations` 大表。

### 最佳实践
1. **分区表**：按时间对操作日志、登录日志进行表分区，提升查询和清理效率。
2. **归档策略**：30 天前的冷数据归档到低成本存储（如对象存储或独立归档表），在线表只保留热数据。
3. **索引优化**：对频繁用于过滤的字段（如 `tenant_id`、`created_at`、`status`）建立复合索引。
4. **软删除替代引用检查**：对删除频次高的业务对象，优先考虑软删除 + 后台异步清理，避免删除时扫描大表。

### 预期收益
- 避免日志表成为性能瓶颈。
- 降低删除操作的延迟。

## 七、API 与代码结构可维护性

### 现状
- 部分业务规则分散在 handler 内部（如学分计算、进度计算）。
- 导入导出、模板下载逻辑分散在各平台 handler 中。

### 最佳实践
1. **领域服务层**：将复杂业务计算（学分、出勤率、能力达成率、排名）抽到 `internal/service` 或 `internal/domain` 中，handler 只负责编排和响应。
2. **模板服务统一化**：将 `TemplateHandler` 升级为通用模板服务，按 entity 类型分发，避免一个 handler 中堆积大量 `ServeXxxTemplate` 方法。
3. **导入管线抽象**：抽取公共导入框架，支持插件式 sheet 解析、行校验、去重策略、事务策略。
4. **统一错误响应与日志**：所有 handler 使用统一的 `respondError` 和结构化日志，便于排查和监控。

### 预期收益
- 降低 handler 复杂度。
- 新增导入导出/模板功能时代码复用率更高。

## 八、优先级建议

| 优先级 | 优化项 | 改动范围 | 预期收益 |
|---|---|---|---|
| P0 | Portal 工作台查询合并 + 短缓存 | `portal_handler.go` + 可选缓存层 | 显著降低入口页延迟 |
| P1 | 统一导入导出为 Excel，抽象导入管线 | `import_export_handler.go`、各 `*_import_handler.go` | 降低维护成本 |
| P1 | 学分等规则配置化 | `platform_configs` + 配置读取层 | 业务调整无需发版 |
| P2 | 商城资源状态机收敛 | `ResourceHandler` + `content_actions.go` | 减少一套状态机 |
| P2 | 大事务拆分与异步化 | `position_handler.go`、`order_handler.go` | 提升并发吞吐 |
| P3 | 审计日志分区与归档 | `operation_logs`、`login_logs`、`view_logs` | 长期性能稳定 |
| P3 | 领域服务层拆分 | 多个 handler | 提升代码可维护性 |

---

## 九、验证方式

- 性能优化：通过压力测试或 A/B 对比关键接口 P99 响应时间。
- 可维护性优化：通过新增功能时的代码改动量、重复代码量评估。
- 配置化优化：验证业务规则变更是否可在不发版的情况下生效。
