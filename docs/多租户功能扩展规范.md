# 多租户功能扩展规范（base-dev-framework6-java）

> 本文档定义在本框架上**扩展多租户功能**的规范标准：适用边界、架构设计、数据库规范、配置规范、代码规范、管理功能与实施步骤。
> 多租户适用于"一套系统服务多家独立企业、租户之间数据完全隔离"的场景。**启用前请先确认系统定位**（见第 1 章）。

## 0. 文档定位与现状说明

⚠️ **当前框架未启用多租户**（已核对源码）：

- `ruoyi-common` 下不存在 `ruoyi-common-tenant` 模块，无 `TenantHelper`、`TenantEntity`、`TenantConstants`
- `MybatisPlusConfig.mybatisPlusInterceptor()` 拦截器链仅注册 **数据权限 / 分页 / 乐观锁** 三个插件，`TenantLineInnerInterceptor` 只出现在类底部注释中
- `scripts/sql/ry_vue.sql` 无 `sys_tenant`、`sys_tenant_package` 表；`ry_workflow.sql` 已按规范预留 `tenant_id varchar(40)` 列
- system 模块与 `ruoyi-api` 契约层无任何租户接口

因此本文档是**扩展规范**，不是"已启用功能的使用说明"。按第 9 章实施清单完成扩展后，方可按第 6~8 章使用。

---

## 1. 适用边界与常见误区

### 1.1 多租户适用场景

- 一套系统**服务多家独立企业**（客户），各客户数据**完全隔离**，互不可见
- 典型形态：SaaS 化交付、平台运营方统一运维、按客户计费

### 1.2 常见误区（不是多租户问题）

以下场景**不应**启用多租户，应使用**数据权限（`@DataPermission`）与业务逻辑**解决：

| 场景 | 为什么不是多租户 | 正确手段 |
|------|----------------|---------|
| 平台内的多商户 | 商户间共享平台运营体系，隔离诉求是行级数据 | 数据权限（按商户维度过滤） |
| 本部 / 分部 | 同企业内组织结构，层级可见 | 数据权限（部门 / 本人） |
| 大租户 / 小租户、上下级租户 | 存在从属与共享关系，非完全隔离 | 业务逻辑 + 数据权限 |
| 用户组 / 角色差异 | 权限层面差异，非数据隔离 | 角色权限（Sa-Token） |

> **总结**：SaaS 的本质是"卖软件"，**客户之间应互不关联**。请确认系统定位满足"客户完全隔离"后再启用多租户。

## 2. 扩展架构设计（新增 `ruoyi-common-tenant` 模块）

多租户基于 **MyBatis-Plus 的 `TenantLineInnerInterceptor` 租户行级插件**实现：
插件在 SQL 执行前解析 AST，自动为带 `tenant_id` 列的表追加 `tenant_id = 当前租户` 过滤条件，INSERT 时自动回填 `tenant_id`。开发者写普通 CRUD，隔离由插件透明完成。

### 2.1 模块与依赖

新建 `ruoyi-common/ruoyi-common-tenant`，依赖：`ruoyi-common-mybatis`、`ruoyi-common-redis`、`ruoyi-common-satoken`、`ruoyi-common-core`。在 `ruoyi-common/pom.xml` 与 `ruoyi-admin` 依赖中引入。

### 2.2 核心类清单

| 类 | 位置 / 来源 | 职责 |
|----|-----------|------|
| `TenantLineInnerInterceptor` | MyBatis-Plus 自带（`com.baomidou.mybatisplus.extension.plugins.inner`） | 租户行级插件：SQL 自动拼 `tenant_id` 过滤 / 回填 |
| `TenantLineHandler`（自定义实现） | `org.dromara.common.tenant.handler` | 提供当前租户 ID（`getTenantId()`）、租户列名（`getTenantIdColumn()`，约定 `tenant_id`）、排除表判断（`ignoreTable()`，读 `tenant.excludes`） |
| `TenantHelper` | `org.dromara.common.tenant.helper` | 租户上下文唯一入口：`ignore` / `dynamic` / `getTenantId` / `isEnable`（静态方法） |
| `TenantConstants` | `org.dromara.common.tenant.constant` | `DEFAULT_TENANT_ID = "000000"`（默认 / 超管租户标识） |
| `TenantEntity` | `org.dromara.common.tenant.core` | 业务实体基类，`extends BaseEntity` 并增加 `tenantId` 字段 |
| `TenantProperties` | `org.dromara.common.tenant.config.properties` | 绑定 `tenant.enable` / `tenant.excludes` 配置 |

### 2.3 插件进链（关键）

在 `ruoyi-common-mybatis` 的 `MybatisPlusConfig.mybatisPlusInterceptor()` 中注册租户插件，**顺序固定**：

```java
@Bean
public MybatisPlusInterceptor mybatisPlusInterceptor() {
    MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
    // 多租户插件（最前：先按租户过滤，再做数据权限等）
    interceptor.addInnerInterceptor(tenantLineInnerInterceptor());
    // 数据权限
    interceptor.addInnerInterceptor(dataPermissionInterceptor());
    // 分页
    interceptor.addInnerInterceptor(paginationInnerInterceptor());
    // 乐观锁
    interceptor.addInnerInterceptor(optimisticLockerInnerInterceptor());
    return interceptor;
}
```

> ⚠️ 判断"隔离是否生效"，第一步永远是确认**插件是否真的 addInnerInterceptor 进链**。

## 3. 数据库设计规范

### 3.1 租户管理表

`sys_tenant`（租户主表，进 `tenant.excludes` 排除表）：

```sql
CREATE TABLE sys_tenant (
    id            bigint       NOT NULL COMMENT '主键',
    tenant_id     varchar(40)  NOT NULL COMMENT '租户编号',
    tenant_name   varchar(100) NOT NULL COMMENT '租户名称',
    domain        varchar(255) DEFAULT NULL COMMENT '绑定域名',
    package_id    bigint       DEFAULT NULL COMMENT '关联套餐ID',
    contact_name  varchar(50)  DEFAULT NULL COMMENT '联系人',
    contact_phone varchar(20)  DEFAULT NULL COMMENT '联系电话',
    status        char(1)      DEFAULT '0' COMMENT '状态（0正常 1停用）',
    expire_time   datetime     DEFAULT NULL COMMENT '过期时间',
    create_by     bigint       DEFAULT NULL,
    create_time   datetime     DEFAULT NULL,
    update_by     bigint       DEFAULT NULL,
    update_time   datetime     DEFAULT NULL,
    PRIMARY KEY (id)
) ENGINE=InnoDB COMMENT='租户表';
```

`sys_tenant_package`（租户套餐表，进 `tenant.excludes` 排除表）：

```sql
CREATE TABLE sys_tenant_package (
    package_id    bigint       NOT NULL COMMENT '套餐ID',
    package_name  varchar(50)  NOT NULL COMMENT '套餐名称',
    menu_ids      text         COMMENT '套餐菜单ID集合（逗号分隔）',
    status        char(1)      DEFAULT '0' COMMENT '状态（0正常 1停用）',
    create_by     bigint       DEFAULT NULL,
    create_time   datetime     DEFAULT NULL,
    update_by     bigint       DEFAULT NULL,
    update_time   datetime     DEFAULT NULL,
    PRIMARY KEY (package_id)
) ENGINE=InnoDB COMMENT='租户套餐表';
```

> 表结构为规范建议，实施时可按业务调整；主键沿用框架雪花 ID（`@TableId`）。

### 3.2 业务表租户隔离规范

让一张业务表参与租户隔离：**建表加 `tenant_id` 列** + **实体继承 `TenantEntity`**。

建表要求（与 `TenantLineHandler.getTenantIdColumn()` 约定一致，参考 `ry_workflow.sql` 既有预留列）：

```sql
CREATE TABLE biz_order (
    id          bigint(20)   NOT NULL COMMENT '主键',
    tenant_id   varchar(40)  DEFAULT '000000' COMMENT '租户编号',  -- 🔴 参与隔离必须有此列
    order_no    varchar(64)  NOT NULL COMMENT '订单号',
    amount      decimal(10,2) DEFAULT NULL COMMENT '金额',
    create_dept bigint(20)   DEFAULT NULL,
    create_by   bigint(20)   DEFAULT NULL,
    create_time datetime     DEFAULT NULL,
    update_by   bigint(20)   DEFAULT NULL,
    update_time datetime     DEFAULT NULL,
    PRIMARY KEY (id)
) ENGINE=InnoDB COMMENT='业务订单表';
```

**排除表规范**（不隔离的表）——通过 `tenant.excludes` 配置（见第 5 章），插件遇到这些表名不追加 `tenant_id` 过滤：

| 表 | 原因 |
|----|------|
| `sys_tenant` | 租户表自身，必须排除否则无法管理租户 |
| `sys_tenant_package` | 租户套餐表 |
| `sys_dict_type` / `sys_dict_data` | 全局字典，所有租户共享 |
| `sys_config` | 全局参数 |
| `sys_menu` | 菜单，全租户共享一套 |

## 4. 实体与代码规范

### 4.1 实体基类：TenantEntity vs BaseEntity

- 本仓库 `BaseEntity` 仅含 5 个公共字段（`createDept` / `createBy` / `createTime` / `updateBy` / `updateTime`），**不含 `tenantId`**
- 扩展后由 `TenantEntity extends BaseEntity` 增加 `tenantId`（String，插件自动维护）
- **需要租户隔离的业务实体继承 `TenantEntity`；不需要的（全局字典、超管配置等）继续继承 `BaseEntity`**

```java
package org.dromara.biz.domain;

import com.baomidou.mybatisplus.annotation.TableName;
import lombok.Data;
import lombok.EqualsAndHashCode;
import org.dromara.common.tenant.core.TenantEntity;

@Data
@EqualsAndHashCode(callSuper = true)
@TableName("biz_order")
public class BizOrder extends TenantEntity {

    private Long id;
    private String orderNo;
    private java.math.BigDecimal amount;

    // 🔴 不要在这里再声明 tenantId：它在父类 TenantEntity 中，由插件自动维护
}
```

### 4.2 铁律（禁止项）

- 🔴 **业务代码不要手动 set `tenantId`**——INSERT 由插件自动回填，手动设置会造成隔离错乱
- 🔴 **不要把 `tenantId` 写进 BO 的查询条件 / VO 输出**——查询过滤由插件透明完成
- 🔴 **不要默认继承 `TenantEntity`**——只有需要隔离的业务实体才继承；全局表继承 `BaseEntity`
- 其余遵循标准 CRUD 约定（`BaseMapperPlus`、`QueryBuilder.lambda`、`@AutoMapper`、BO 入参 / VO 出参）

### 4.3 与数据权限共存

- 租户插件负责"租户级"行过滤，`@DataPermission`（`PlusDataPermissionInterceptor`）负责"部门/本人"级行过滤，二者**叠加生效**，互不冲突
- 仅在忽略租户过滤的同时需保留数据权限时，注意 `@InterceptorIgnore` 的用法（见 6.1）

## 5. 配置规范

`application.yml`（或 `common-tenant.yml`）：

```yaml
tenant:
  # 多租户总开关
  enable: true
  # 排除表：这些表不参与租户隔离（所有租户共享 / 由自身语义决定）
  excludes:
    - sys_tenant
    - sys_tenant_package
    - sys_dict_type
    - sys_dict_data
    - sys_config
    - sys_menu
```

- `enable`：控制多租户总开关
- `excludes`：不需要租户隔离的表在此配置排除；**表里有 `tenant_id` 列但不想自动过滤的表必须配进 excludes**（如 `sys_tenant`）
- **改 excludes 需重启应用**（插件配置在启动时一次性加载）
- ⚠️ **如果已基于租户模式启动过程序，关闭租户必须删除 MySQL 与 Redis 内的相关数据，重新导入 SQL**

## 6. 忽略与动态切换规范

### 6.1 Mapper 层忽略（`@InterceptorIgnore`）

指定单独 SQL 不开启租户过滤时，在对应 Mapper 接口添加：

```java
@InterceptorIgnore(tenantLine = "true", dataPermission = "false")
List<XxxVo> selectAllTenantList(...);
```

> 🔴 **注意事项**：使用此注解时 `dataPermission = "false"` **必须显式添加**——MyBatis-Plus 的 `@InterceptorIgnore` 默认会同时忽略数据权限拦截，不显式关闭会导致数据权限失效。

### 6.2 业务层忽略（推荐）：`TenantHelper.ignore(...)`

临时忽略租户过滤查全量（超管跨租户统计、定时任务遍历所有租户等），**自动 try-finally 回收**，lambda 结束后上下文恢复：

```java
// 无返回值
TenantHelper.ignore(() -> {
    // 这里查的是所有租户的数据
    bizOrderMapper.selectList(null);
});

// 有返回值
Long total = TenantHelper.ignore(() -> bizOrderMapper.selectCount(null));
```

### 6.3 动态切换租户：`TenantHelper.dynamic(租户id, ...)`

仅适用于特殊需求业务（创建租户时初始化该租户数据、跨租户查数据等）。**禁止乱用，后果自负**：

```java
// 无返回值
TenantHelper.dynamic("100001", () -> {
    bizOrderMapper.insert(order); // 自动回填 tenant_id = 100001
});

// 有返回值
Long count = TenantHelper.dynamic("100001", () -> bizOrderMapper.selectCount(null));
```

底层成对方法（一般用上面 lambda 封装，不直接手调）：

```java
TenantHelper.setDynamic("100001"); // 设置动态租户
try {
    // 在 100001 租户下执行
} finally {
    TenantHelper.clearDynamic(); // 🔴 必须 finally 清理，否则污染线程后续请求
}
```

### 6.4 ignore vs dynamic 区别

| 能力 | 方法 | 效果 | 典型场景 |
|------|------|------|---------|
| 忽略隔离 | `TenantHelper.ignore(...)` | 这段逻辑内**不加任何** `tenant_id` 过滤，查所有租户 | 超管跨租户统计、全局清理 |
| 动态切换 | `TenantHelper.dynamic(id, ...)` | 这段逻辑内**强制按指定租户**过滤 / 回填 | 超管代某租户操作、跨租户搬数据 |
| 默认（不调） | 无 | 按**当前登录用户**所属租户自动过滤 | 普通业务请求 |

记忆法：`ignore` = "看全部"，`dynamic` = "扮演某个租户"，默认 = "只看自己租户"。

### 6.5 取当前租户 / 判断启用

```java
String tenantId = TenantHelper.getTenantId();   // 当前请求线程绑定的租户编号
boolean enable = TenantHelper.isEnable();        // 多租户是否启用（tenant.enable=true 且插件已加载）

// 判断是否超管租户：用常量，不要硬编码字符串 "000000"
boolean isSuper = TenantConstants.DEFAULT_TENANT_ID.equals(TenantHelper.getTenantId());
```

## 7. 登录与租户上下文扩展

### 7.1 登录流程扩展点（基于现有架构）

- **登录接口**：`AuthController` 的 `POST /login`，入参 `LoginBody` **增加 `tenantId` 字段**；`SysLoginService` 登录前校验租户状态（停用 / 过期），登录成功后把租户写入登录用户上下文
- **租户列表接口**：新增 `GET /tenant/options`（或复用 `ruoyi-api-system` 契约），供登录页展示可选租户
- **域名绑定**：若租户配置了绑定域名，登录页仅展示**当前域名相关**的租户列表

### 7.2 登录界面（租户选择）

- 未绑定域名：登录页下拉选择租户
- 已绑定域名：自动锁定当前域名对应租户

### 7.3 切换租户（仅超级管理员）

- **管理员切换租户不是切换用户，切换的只是数据**——管理员拥有所有权限
- 仅超管（`DEFAULT_TENANT_ID` 租户）可操作；切换后当前会话按目标租户过滤数据

## 8. 管理功能规范（套餐 / 租户）

### 8.1 租户套餐管理

- **先新增套餐，再新增租户**——租户新增之后**无法修改所选套餐**（跟钱挂钩，属于计费约束）
- 套餐关联的菜单后续被修改时，可对目标租户执行**同步套餐**

### 8.2 租户管理

| 操作 | 说明 |
|------|------|
| 默认租户 | **无法修改**（`DEFAULT_TENANT_ID` = "000000"） |
| 新增租户 | 填写表单（名称/域名/联系人/过期时间等）+ 选择租户套餐 |
| 修改租户 | 可配置域名（用于绑定租户到特定域名）；未配置域名则登录页展示全部租户 |
| 登录租户 | 用该租户管理员账号登录后进入对应租户空间 |

### 8.3 同步套餐（强调：这不是 Bug）

- **应用场景**：租户套餐被修改后，把套餐的菜单权限**重新同步**到特定租户（不是所有租户都有更新套餐的权利——这与计费挂钩）
- **补充说明**：
  1. "同步套餐"本质是把**当前套餐关联的菜单权限**重新同步到目标租户
  2. 主要影响**租户管理员及其角色可分配的菜单范围**，**不是重置租户业务数据**
  3. 若后续还调整了默认租户下的字典、参数等基础配置，通常还需配合同步字典 / 参数等能力一起处理

## 10. 注意事项与常见问题

| 问题 | 处理 |
|------|------|
| 租户隔离不生效 | 按序排查：① 插件是否进链（最常见）→ ② `tenant.enable` 是否 true → ③ 表是否有 `tenant_id` 列 → ④ 实体是否继承 `TenantEntity` → ⑤ 表是否被误加进 `excludes` → ⑥ 是否包在 `ignore` 块内 |
| 查不到别的租户数据 | 属隔离正常生效；期望跨租户请用 `TenantHelper.ignore(...)` / `dynamic(...)` |
| 关闭多租户 | 必须删除 MySQL 与 Redis 内的相关数据重新导入 SQL（`tenant_id` 残留会导致数据错乱） |
| 改 `excludes` 不生效 | 需重启应用（插件启动时一次性加载） |
| 原生 SQL / union / exists 漏过滤 | 插件解析不了的复杂 SQL 可能漏过滤；优先用 `selectList` + Wrapper 等标准方式 |
| `@InterceptorIgnore` 后数据权限失效 | `dataPermission = "false"` 必须显式添加（MyBatis-Plus 默认同时忽略数据权限） |
| `tenant_id` 值不对 | 确认实体继承 `TenantEntity`、未手动 set `tenantId`；INSERT 由插件回填 |
| 判断超管租户 | 用 `TenantConstants.DEFAULT_TENANT_ID.equals(TenantHelper.getTenantId())`，**不要硬编码 "000000"** |
